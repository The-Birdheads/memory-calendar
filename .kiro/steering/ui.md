# UI/デザイン基本ルール

このドキュメントは本アプリ（Expo/React Native、iOS/Android、現状ライトモードのみ）のUI実装における基本ルール。
新規画面の実装・既存画面の改善は、原則としてこのルールに従う。個別画面のspecで明示的に上書きされた場合はspec側を優先する。

## 1. 設計の進め方

画面を作る/直すときは、見た目の指摘だけでなく次を先に明確にする:
- そのユーザーがこの画面で何をしたいか（主目的）
- 最も優先される操作は何か
- 片手操作を想定し、主要操作は画面下部〜中央（親指の届く範囲）に置く

一気に全画面を変えず、1画面ずつ実装→シミュレータ/実機で確認→次の画面、のサイクルで進める。

## 2. カラーパレット

既存実装（calendar/event画面）から抽出した現状のパレットを正とする。新規色を増やす場合もこの体系に合わせる。

| 用途 | 色 | 備考 |
|---|---|---|
| プライマリ（アクション、選択状態、リンク） | `#2f6fed` | ボタン、選択中タブ、強調テキスト |
| プライマリの薄色背景（選択中チップ等） | `#e8f0fe` | プライマリの背景バリエーション |
| エラー/削除 | `#d32f2f` | 削除ボタン、エラーテキスト |
| エラー（濃） | `#e53935` | エラーバッジ等、d32f2fと使い分けず統一を検討 |
| 背景（画面） | `#fff` / `#fafbfc` | 画面全体は白、セクション区切りに薄グレー |
| 背景（カード/行の区切り） | `#f2f3f5` | |
| テキスト（本文濃） | `#000` / `#444` | 見出し・主要テキスト |
| テキスト（本文薄） | `#666` | 補足テキスト |
| テキスト（プレースホルダ/無効） | `#999` / `#888` | |
| ボーダー/区切り線 | `#ccc` | |
| 評価（★、記録の振り返り用） | `#f0a942` | 献立の評価星のみで使う専用トークン。★評価という世界共通の慣習に合わせた例外で、プライマリブルーでは代用しない |

**60/30/10ルール**を意識する: 背景の白/薄グレーが60%、テキストのグレー系が30%、プライマリブルーや警告色などのアクセントは10%程度に抑える。新しいコンポーネントで色を追加する前に、上記で代替できないか確認する。

## 3. タイポグラフィ

サイズは既存実装で使われている以下の段階に統一し、むやみに増やさない:

| 用途 | fontSize | fontWeight |
|---|---|---|
| 画面タイトル/大見出し | 20〜28 | 700 |
| セクション見出し | 16〜18 | 700 |
| 本文/ボタンラベル | 14〜16 | 600〜700（強調） / 通常時は指定なし |
| 補足・キャプション | 12〜13 | 通常 |
| 極小ラベル（バッジ等） | 9〜10 | 通常 |

fontWeightは `"700"`（強調）と `"600"`（やや強調）の2種類を基本とし、通常テキストは指定しない。太さのバリエーションを増やさない。

## 4. スペーシング/グリッド

- 8ptグリッドを基本とする（4, 8, 12, 16, 24, 32…の倍数で余白・パディングを揃える）
- カード/セクション間の余白は16、要素内の余白は8〜12を目安にする
- **各ブロック（スイッチャー行・サマリー行・セクション見出しなど）は自分の下側の余白（`paddingBottom`/`marginBottom`）を自分で持つ**。`paddingTop`だけで済ませて次に来る要素の余白に頼らない（次の要素が空表示や条件付きレンダリングだと余白ごと消える）。実例: `todos.tsx`の`summaryRow`が`paddingTop`のみで`paddingBottom`を持たず、直後の要素との間に余白が無くなっていたバグを`paddingVertical`化して修正した。新しいブロックを追加するときはこのチェックを行う。
- 逆に、隣接する2要素が両方とも余白を持つと二重になる（例: カードの`marginBottom`と次のセクションの`marginTop`を両方入れない）。片方（基本は前の要素の`marginBottom`/`paddingBottom`）に統一する。

## 5. 角丸（borderRadius）

既存実装の段階に合わせる:
- 小さいチップ/バッジ: `3〜5`
- ボタン/入力欄/カード: `8〜12`
- 大きいモーダル/シート: `16`
- 円形に近いアイコンボタン/FAB: `20〜28`（サイズの半分程度）

## 6. アイコン/絵文字（2026-09追加）

意味を表す小さな図（鍵・追加・グリッド/一覧・カテゴリなど）は、**カラー絵文字(🔒📷✨🎲など)ではなく`src/shared/components/Icon.tsx`のアイコンアセットを使う**。カラー絵文字はOS/端末によって見た目が大きく変わり、他の画面のモノクロアイコン体系とも馴染まないため。

- **アイコンアセットの追加方法**: `assets/icons/*.png`（96×96、透明背景・黒一色のRGBA PNG、内容の外周に約10pxの余白）を追加し、`Icon.tsx`の`ICONS`マップに登録する。`tintColor`で呼び出し側が好きな色に塗り替えられる「テンプレート画像」なので、アセット自体は黒一色でよい。既存アセットで意味が近いものがあれば新規作成せず流用する（例: グリッド表示の切り替えボタンには`calendar`ではなく専用の`grid`/`list`を追加したが、"錠前"はどの画面でも既存の`lock`をそのまま使う）。
- **許容される例外(絵文字ではなく記号として扱う)**: `‹›`（月送り矢印）、`☐☑`（チェックボックス）、`✓✕`（確定/キャンセル）、`★☆`（評価)、`⋯`（もっと見る）のような、単色でTextの`color`スタイルからそのまま塗り替えられる記号的なUnicodeグリフは、専用アイコンアセットを作るほどでもない軽量な代替として許容する。判断基準は「その文字がOS/フォントによらずほぼ同じ単色の記号として描画されるか」－色つきの絵文字(🔒📷✨🎲🍽️📝など)はこれに当たらないので使わない。
- **失敗例**: カレンダー画面のグリッドセル内で、個人カレンダーの予定を🔒(カラー絵文字)をタイトルの前に付けて示していたが、上記ルールに反するため`Icon name="lock"`(既存のロックアイコン、`size=7`程度の極小サイズでも使える)に置き換えた(2026-09)。新しく「種類を見分ける印」を追加する場合はこの失敗を繰り返さない。

## 7. タップ領域・親指ゾーン

- タップ可能な要素は最低 `44×44pt` を確保する（見た目が小さいアイコンでも `hitSlop` で拡張する）
- タブバー、主要アクションボタン（追加・保存・確定など）は画面下部に配置する
- 破壊的操作（削除など）は誤タップしにくい位置・見た目（エラー色 `#d32f2f`、確認ダイアログ）にする
- **新規追加のFAB(丸いプラスボタン)の規格**（2026-09、献立タブに合わせて統一）: 右下固定・`position: "absolute"`、`right: 16` / `bottom: 20`、サイズ`52×52`・`borderRadius: 26`、背景`#2f6fed`、影は`shadowColor:"#000", shadowOpacity:0.2, shadowRadius:6, shadowOffset:{width:0,height:2}, elevation:4`。中身は生の`+`文字ではなく`<Icon name="plus" size={22} color="#fff" />`（アセットのプラスアイコン、他のアイコンと同じモノクロPNG体系に揃える）。カレンダー画面(`calendar-add-event-fab`)・献立タブ各パネル(`meals-plan-add`/`meals-log-add`)で共通。新しく「画面に1つだけ置く追加系FAB」を作る場合はこの数値をそのまま使う。

## 8. 既存の確立済みUIパターン（踏襲する）

- **モーダルは範囲外タップで閉じる**（2026-09追加、全モーダルに徹底）: 半透明の背景(オーバーレイ)を持つモーダル(確認ダイアログ、フォーム、シート類)は、必ずカード外側のタップでキャンセル/クローズできるようにする。実装は「オーバーレイ全体を`TouchableOpacity`(`activeOpacity={1}`、`onPress`にキャンセル/クローズ処理、`testID`は`{何の}-backdrop`)にし、その内側のカードをもう一枚の`TouchableOpacity`(`activeOpacity={1}`、`onPress={() => {}}`でタップを吸収し伝播させない)で包む」という組み合わせで統一する(`SettingsHubModal`（とそこから遷移する各画面）が最初からこの形で、他の全モーダルもこれに揃えた)。破壊的操作の確認ダイアログ(削除など)でも安全に適用してよい - 範囲外タップは常に「キャンセル」相当であり、間違って確定(削除)されることはない。
  - **下からせり出すフォーム(bottom sheet、`KeyboardAvoidingView`→`ScrollView`(`flexGrow:1, justifyContent:"flex-end"`)→カード、の形)の場合**: `ScrollView`を`TouchableOpacity`(`flex:1`、`onPress`でクローズ)で包み、カード自体もその内側でもう一枚`TouchableOpacity`(`activeOpacity={1}`, `onPress={() => {}}`)にする。カレンダー画面の予定作成モーダル・`EventDetailContent`の予定編集モーダルがこの形。
  - **中央寄せのカード(センターダイアログ)にテキスト入力欄がある場合も、同じ理由でキーボード対策が必須**（2026-09追加）: 見た目はbottom sheetでなく中央寄せの角丸カードのままでも、`TextInput`を含むモーダルは同じく`KeyboardAvoidingView`(iOSは`behavior="padding"`)で包まないと、キーボードが開いた時に入力欄やその下のボタン(保存・削除など)が隠れて操作できなくなる(実際に献立の詳細入力画面でURL/メモ欄がキーボードに隠れて入力できない不具合として発覚)。中央寄せの場合は、`KeyboardAvoidingView`自身には`justifyContent`/`alignItems`を持たせない(持たせると内側の`TouchableOpacity`が横幅いっぱいに広がらず、範囲外タップでのクローズが効かなくなる) - 中央寄せは`KeyboardAvoidingView`→`TouchableOpacity`(backdrop、`flex:1`)→`ScrollView`(`contentContainerStyle`に`flexGrow:1, justifyContent:"center", alignItems:"center"`)→カード、という構成にし、中央寄せをScrollView側の`contentContainerStyle`に持たせることで、キーボード表示時にカードが自動的に押し上げられ、かつ内容がカードの高さを超える場合はスクロールもできるようにする。`MealFormModal`(献立の詳細)・`ReattachTodoModal`(ToDoの予定紐付け、「新規予定を作成」フォーム部分のみ)・`SettingsHubModal`(カレンダー/タグ設定などの各画面)がこの形。`ReattachTodoModal`の「既存の予定を選ぶ」側のように中身が`FlatList`の場合は(`ScrollView`にネストすると警告が出るため)対象外でよい - `FlatList`自体が自前でスクロールする。
  - **Modalでない、ページ全体のフォーム(ログイン・サインアップ画面など)の場合**: `Modal`が無いのでbackdropの仕組みは不要だが、キーボード対策自体は同じ - 画面を`KeyboardAvoidingView`(`flex:1`、iOSは`behavior="padding"`)で包み、その中の`ScrollView`の`contentContainerStyle`に元々`View`が持っていたレイアウト(`flexGrow:1, justifyContent:"center", padding`等)をそのまま移す。`app/(auth)/login.tsx`・`signup.tsx`がこの形。
  - **新しくテキスト入力を含むモーダル/画面を作る場合のチェック**: 見た目が中央寄せかbottom sheetか、Modalか通常画面かに関わらず、`TextInput`を1つでも含むなら`KeyboardAvoidingView`(iOS: `behavior="padding"`)で包んであるか必ず確認する。内容が短くても、後から項目を追加した時に同じ問題が再発しないよう最初から対応しておく。
  - **例外**: `EventDetailModal`(`EventDetailContent`を全画面スライド表示するラッパー)のようにカードが画面全体を覆い「外側」が視覚的に存在しないフルスクリーンの画面は対象外(戻る矢印やAndroidの戻るボタン`onRequestClose`で閉じる)。
  - **新しいモーダルを作る/直す際のチェック**: `<Modal>`を書いたら必ずこのパターンに従っているか確認する。`onRequestClose`(Android物理戻るボタン対応)も併せて渡す。
- **設定画面は単一の画面スタックで統一する**（2026-09追加）: 設定まわり（個人設定/カレンダー設定/カレンダー作成・参加・招待/タグ管理）は、以前は`SettingsHubModal`の`Section`状態・`CalendarSettingsContent`独自の`Mode`状態・`TagManagementModal`独自の`Mode`状態・`InviteFlowModal`という4つのモーダル/状態が入れ子になっており、`CalendarSettingsContent`が非listモードの間は`SettingsHubModal`自身の「← 設定に戻る」と`CalendarSettingsContent`の「← 一覧に戻る」が同時に表示される、という戻るボタン重複バグがあった。これを解消するため、`SettingsHubModal`が単一の`Screen[]`スタック（`push`/`pop`/`replace`の3操作のみ）を持ち、他の画面(`CalendarSettingsScreens.tsx`の各`*Screen`、`TagManagementScreens.tsx`の各`*Screen`、`InviteScreen.tsx`)は自前のModal/ヘッダー/戻るボタンを一切持たない「中身だけ」のコンポーネントにした。ヘッダーは`SettingsHubModal`が1箇所だけ描画し、常に`[← 戻る(スタックが2以上の時のみ、pop) / 画面タイトル / × 閉じる(常時、onClose)]`の3要素で、画面ごとに戻り先ラベルを変える（「設定に戻る」「一覧に戻る」等）ことはしない。新しく設定配下に画面を足す場合も、独自のModal/戻るボタンを作らず、`Screen`判別共用体に1バリアント追加して`SettingsHubModal`からpush/popで遷移させる。
  - **設定ハブのトップ一覧**: 「個人設定」「カレンダー設定」「タグ設定」の3項目(`settings-hub-open-personal`/`settings-hub-open-calendar`/`settings-hub-open-tags`)。タグはカレンダーに紐付かない個人単位の設定(タグ管理画面自体の実装も参照)なので、特定のカレンダーの編集画面を経由しなくても直接たどり着けるようにハブ直下に置く(2026-09追加 - 元々`タグ管理`は「カレンダー設定→カレンダーを選ぶ→タグ管理」の3手先にしかなく、ハブから直接たどり着けなかった)。`CalendarEditScreen`の「タグ管理」ボタン(`calendar-settings-manage-tags`)からも同じ`tag-list`画面へ遷移できる、もう1つの入り口として残す(予定にタグを付ける文脈でカレンダー編集からもすぐ開けると便利なため)。
  - **← 戻る / × 閉じる**: 戻るは記号的なUnicodeグリフ`←`をText表示（[6章](#6-アイコン絵文字2026-09追加)の許容例外に追加）。閉じるは`Icon name="close"`（既存の×アイコンアセット）を使い、テキストの「閉じる」ボタンは設定画面から無くした。testIDは`settings-hub-back`/`settings-hub-close`で固定(スタックの中身が何であってもこの2つだけ)。
- **複数選択チップの「デフォルト全選択・タップでトグル」パターン**: カレンダー/ToDo/振り返り(年表・画像とも)/mealsタブで採用済み。新しい絞り込みUIを作る際もこのパターンを踏襲する（`selectedIds: Set<string> | null` で null=全選択、タップで個別トグル）。「すべて」チップは作らない。
- **カレンダー選択チップ**: `src/features/calendars/components/CalendarSwitchChip.tsx` を使う（calendar/todos/history(年表・画像とも)/mealsタブで共通化済み）。枠線1px→選択時2px、選択時は背景`#e8f0fe`+チェックマーク(✓)+文字色`#0c447c`で強調。見た目を変える場合はこのコンポーネント1箇所を直せば全画面に反映される。
- **保存/キャンセル/削除は文言ではなくアイコン・記号で表す**（2026-09見直し、元は「編集確定は✓/✕ボタン」としてタグのインライン編集のみが対象だったが、アプリ全体の同種ボタンに拡張した）: 直感的な操作のため、この3種の汎用アクションはテキストラベルではなくアイコン/軽量なUnicodeグリフに統一する。
  - **保存(確定)**: `✓`のテキストグリフ（[6章](#6-アイコン絵文字2026-09追加)の許容例外）。予定詳細のタグ編集などのインライン編集や、各種フォームの保存ボタンで使う。画面遷移での自動保存に頼る場合も、離脱時に確実に保存されることをテストで担保する。
  - **キャンセル**: `✕`のテキストグリフ。保存・削除の確認ボタンと対で使う「このフォーム/編集を取りやめる」インライン操作が対象。モーダル/パネル全体を閉じる見出し行の「閉じる」ボタン（`Icon name="close"`の×アイコンアセット、[設定画面の「← 戻る/× 閉じる」](#8-既存の確立済みuiパターン踏襲する)参照）とは役割が異なるため、こちらは既存の`Icon name="close"`のまま変更しない。
  - **削除**: `Icon name="trash"`（既存のゴミ箱アイコンアセット、`color="#d32f2f"`）。「削除」単体ボタンや、削除確認モーダルの確定ボタンが対象。ただし「カレンダーを削除しますか?/このカレンダーから抜けますか?」のように削除以外の意味(退出など非破壊的操作)を兼ねるボタンは、その意味の時だけ元のテキストのままにする(`LeaveOrDeleteCalendarConfirmModal`の`willDeleteEntirely=false`時の「抜ける」など)。「予定を削除」のような、単語単体ではなく具体的な対象名を含む説明的なCTA文言（削除以外の「作成」「参加」「招待する」なども同様）はこの対象外(文言のままでよい)。
  - 変換したボタンには`hitSlop={{top:10,bottom:10,left:10,right:10}}`を付け、44×44pt相当のタップ領域を確保する([7章](#7-タップ領域)のルールと同じ)。
  - 対象化した箇所（2026-09時点）: `LeaveOrDeleteCalendarConfirmModal`/`DeleteTagConfirmModal`/`DeleteEventConfirmModal`（キャンセル・削除）、`CalendarSettingsScreens`の`CalendarEditScreen`保存・`EditTagForm`保存・`PersonalSettingsPanel`保存（保存単体）、`MealFormModal`（本体の削除・キャンセル・保存＋削除確認ダイアログのキャンセル・削除）、`EventCommentsSection`の自分のコメント削除、`EventDetailContent`のToDo項目削除・予定編集モーダルのキャンセル/保存、`calendar.tsx`の予定作成モーダルのキャンセル・ToDoチェックリスト項目削除、`todos.tsx`の削除確認モーダルのキャンセル・削除。新しく同種のボタンを作る場合もこの3パターンを踏襲する。

    - **セクションの並び順**: リマインド→タグ→ToDo→思い出→コメント(2026-09指定)。リマインドは指定対象外だったが、個人用枠の先頭(タグより前)に据え置いた。グループカレンダーではこの順で個人用枠→共有枠、個人用カレンダーでもこの順のまま単一の枠に並ぶ。
    - 新しく予定詳細に項目を追加する場合も、その項目がカレンダーメンバー全員に見えるか自分専用かをまず判断し、対応する枠(グループカレンダーなら共有枠か個人用枠、個人用カレンダーなら常に単一の個人用枠)の中に、上の並び順を保ったまま置く。実装は各セクションのJSXを`commentsSection`/`memoriesSection`/`reminderSection`/`tagsSection`/`todoSection`という変数として1度だけ組み立て、`EventDetailContent.tsx`内でカレンダー種別によって枠の組み方だけを出し分ける(セクションのJSX自体を2重に書かない)。
  - **予定詳細の「編集」「追加」はアイコンのみ**（2026-09追加）: タイトル横の編集ボタン(`event-edit-button`)・タグ欄の編集ボタン(`event-tags-edit-button`)は`Icon name="edit"`(鉛筆、新規追加アセット)、ToDo追加(`event-todo-add`)・写真追加(`event-photo-add`)は`Icon name="plus"`のみで、「編集」「追加」という文言のテキストボタンは置かない(タップ領域は`hitSlop`で44pt相当に拡張)。タグ欄の空状態メッセージ「タグはまだありません（編集から追加できます）」のような説明文中の「編集」という言葉自体は残してよい(ボタンラベルではなく文章の一部のため)。
  - **予定作成モーダルも同じ共有/個人用の枠と背景色で分ける**（2026-09追加）: `app/(tabs)/calendar.tsx`の予定作成モーダルにも、予定詳細画面と同じ配色ルールを適用した。カレンダー選択チップ(`event-create-calendar-{id}`)は「共有/個人のどちらに属するかを選ぶコントロール自体」なのでどちらの枠にも入れず素のまま置き、選んだカレンダーの種別で以降の中身の枠分けを決める。
    - **共有カレンダー向け**: 予定情報(タイトル・終日・日時・場所・URL、`EventFormFields`)を青い共有枠(`event-create-shared-frame`)に、タグ・ToDoをグレーの個人用枠(`event-create-personal-frame`、`PersonalOnlyBadge`付き)に分ける。
    - **個人用カレンダー向け**: 共有相手がいないため、予定情報・タグ・ToDoをすべて1つのグレーの個人用枠にまとめる(青い共有枠は出さない) - 予定詳細画面の個人用カレンダーの扱いと同じ考え方。

    - **枠の中の入力欄・チップは白地のまま**（2026-09見直し）: 青/グレーの枠の背景色がテキスト入力欄(`TextInput`)やタグチップにまで透けると、「入力できる場所」なのか単なる背景の一部なのか直感的にわかりづらく、触っていいのか迷わせてしまう。`EventFormFields`/`RevealableTextField`の`input`・`dateField`スタイルと`TagPickerRow`の`chip`スタイル(未選択時)には明示的に`backgroundColor: "#fff"`を指定し、枠の色に関わらず常に白地で浮き上がって見えるようにする。新しく枠の中に入力欄やチップを置く場合も、背景色を明示しないと親の枠色が透けてしまう点に注意する。
    - **「+ ToDoを追加」も場所/URLと同じ見た目に統一**（2026-09見直し）: 元は「ToDoを追加する」というスイッチ＋チェックマークの行だったが、同じ「任意項目を追加する」操作なのに`RevealableTextField`(「+ 場所を追加」)と見た目が違っていた。`Icon name="plus"`＋「ToDoを追加」という同じ文言パターンのボタン(`addFieldButton`/`addFieldButtonText`スタイル、`RevealableTextField`の見た目を`calendar.tsx`側にも複製)に統一し、タップしたら(場所/URLと同様)チェックリストを表示したまま引っ込めない一方向の挙動にした(スイッチのOFFに戻す操作は廃止)。

- **ToDoのリマインドは予定と同じ選択式UI、ベル自体がボタン**（2026-09見直し）: 以前はISO日時を生テキストで直接入力させ、別に置いた歯車アイコン(`todo-settings-{id}`)からしか開けなかった。`src/features/todos/components/TodoReminderPicker.tsx`を新設し、予定詳細の`EventReminderPicker`と同じ選択肢(終日の予定なら当日/1日前/2日前、時刻指定なら開始時/10分前/1時間前＋カスタム時刻)を再利用する(`EventReminderPicker.tsx`から`ALL_DAY_OPTIONS`/`TIMED_OPTIONS`/`WheelColumn`等をexportして共有)。ただしToDo自体は`reminder_at`1件しか持てない(予定のように複数のリマインドを追加できるリストではない)ため、単一選択(既に選ばれている選択肢をもう一度押すと解除、別の選択肢を押すと置き換え)にしている。選択肢から実際の通知時刻(絶対時刻)を計算する処理はDBの`compute_event_reminder_at`(トリガーでの自動計算)と全く同じ式を`src/features/events/reminderCompute.ts`の`computeEventReminderAt`としてクライアント側に再現したもの(ToDoは予定と違いクライアントが絶対時刻を直接保存するため、DBトリガーに頼れない)。
  - **開閉の入り口はベルのアイコン自体**: 歯車ボタンは廃止し、ベル(`todo-reminder-icon-{id}`、オン/オフ問わず常にタップ可能)を押すとそのままリマインド設定モーダルが開く。モーダルには×アイコンの閉じるボタン(`todo-reminder-close-{id}`)を付け、範囲外タップ(`todo-reminder-backdrop-{id}`)でも閉じられる(8章冒頭の「モーダルは範囲外タップで閉じる」ルールに準拠)。
  - **何も選ばず閉じれば必ずベルはオフのまま**: 各選択肢は押した瞬間に確定・保存する(予定のリマインドと同じ、別の「保存」ボタンは無い)ので、何も押さずに閉じれば`todos.reminder_at`は変化せず、ベルは(元々オフだった場合)オフ表示のまま維持される。旧実装はテキスト欄を空のまま保存すると空文字列`""`が保存され`!== null`判定でベルがオンに見えてしまうバグがあったが、この設計ではそもそも「何もしない」場合に何も保存されないため発生しない。
- **献立タブ(予定/記録の統合タブ)**（2026-09見直し）: `app/(tabs)/meals.tsx`。振り返りタブと同じ「統合タブ内に独立したパネルを複数持たせる」構成を踏襲し、`meals-mode-switch`で「予定」「記録」を切り替える。「予定」はあらかじめ決めた献立を忘れずに食べるためのパネル(未来の`mealDate`、日付見出しのみでグルーピング)、「記録」は食べたものを振り返って次の献立の参考にするためのパネル(過去の`mealDate`、新しい順に月見出し→日付見出しの2段でグルーピング、`src/features/meals/grouping.ts`)。同じ日の中の並び順は時系列(朝→夜)ではなく**間食→夕食→昼食→朝食**の指定順（`groupMealsByDate`内の`SLOT_DISPLAY_ORDER`）。
